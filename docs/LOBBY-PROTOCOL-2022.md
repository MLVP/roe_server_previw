# Протокол лобби ROE 2022: что клиент шлёт и что значит

Источник: живой захват `lobby/20261022T042028-lobby-c45f5d/` (клиент в лобби,
пользователь перебирал режимы, искал друга, вводил код, создавал кастом-сессию).
Всё расшифровано по кадрам `packets.log` (AES-128-CBC, ключ
`private/candidate-001.key`).

## Сообщения клиента, которые мы поняли

| код | что | тело |
|---|---|---|
| `0x2f0` | Login_Hello_v3 | uid клиента по смещению 42 (BE32) |
| `0x702f` | TEAM_PULL_INFO | 1 байт (`0x0b`) |
| `0x701d` | TEAM_CREATE_REQ | 4×u32: (2, map_id, перспектива, 0) |
| `0x6e29` | **запрос подбора** | 5×u32: (режим, ?, перспектива, тип, map_id) |
| `0x6e2b` | отмена подбора | 1 байт |
| `0x7371` | **создание кастом-сессии** | см. ниже |
| `0x1249` | поиск друзей | u32 длина + ASCII + NUL: `TEST_FRIEND` |
| `0x730d` | бонусный код | u32 длина + ASCII + NUL: `43215678` |
| `0x7021` | обновление списка подбора | 1 байт |
| `0x703b` / `0x702b` | переключение вкладок (друзья / недавно игравшие) | u32: 1 или 2 |
| `0x7149` | периодический keepalive | u32 (время) |
| `0x1f74`, `0x1a37`, `0x3783`, `0x1b59`, `0x71ae` | фоновые синхронизации клиента | — |

## Запрос подбора `0x6e29` - главное

Тело 20 байт = 5 u32 (big endian):

| слово | значение | примеры из захвата |
|---|---|---|
| 0 | режим | 1 = Solo, 4 = Squad |
| 1 | неизвестно | всегда 1 |
| 2 | перспектива | 1 = TPS (третье лицо), 2 = FPP (от первого) |
| 3 | тип подбора | 1 = обычный (auto-matching), 2 = тренировка (vs AI) |
| 4 | id карты | 16007 Europa (Kill Zone), 16010 Dion, 16021 Vera, 16023 карта тренировки |

Захваченные запросы (в порядке действий пользователя):

```
Squad,  FPS,  Europa    -> 4, 1, 2, 1, 16007
Solo,   FPS,  Europa    -> 1, 1, 2, 1, 16007
Solo,   TPS,  Europa    -> 1, 1, 1, 1, 16007
Solo,   FPS,  Europa    -> 1, 1, 2, 1, 16007
Solo,   FPS,  Training  -> 1, 1, 2, 2, 16023
Solo,   TPS,  Training  -> 1, 1, 1, 2, 16023
```

Значит сервер получает всё, что нужно: режим, перспектива, тип и карта.
Ответы сервера в этом сценарии: `0x6e2a` (подбор принят) на каждый запрос
и `0x6e2c` (результат) на каждую отмену. `0x6e2d` (MATCH_SYNC) не
уходил - игрок отменял раньше, чем проходили 5 секунд ожидания.

## Кастом-сессия `0x7371`

```
u32  0
u32  0
u64  actor_uid игрока
u32  длина имени + "awp" + NUL
u32  1
u32  режим        (1 = Solo, 4 = Squad)
u32  перспектива  (2 = FPP)
u32  0
u32  id карты     (16007 Europa, 10120 Dion, 16021 Vera)
u32  максимум игроков (60)
u32  0
u32  0
```

С паролем тело длиннее на 8 байт: сразу после имени идёт
`u32 длина + "12345678" + NUL` - тот же формат строки, что у поиска друзей
и бонусного кода.


## Какая комната запускается

Комнат может быть несколько, и лобби выбирает их **по карте из запроса
подбора** (`0x6e29`, слово 4 - id карты).

1. Менеджер комнат поднимает комнату (режим из `config/services/room.json`
   -> `modes/<режим>/mode.json` -> `map.id` и `route`) и регистрирует её
   в лобби: `GET /api/room?route=0:127.0.0.1:18001&map_id=16010&instance_id=1`.
2. Лобби хранит комнаты по id карты (`GET /api/status` -> `rooms`).
3. Когда клиент присылает `0x6e29` с картой, лобби отдаёт в `0xd77/0xd76`
   именно её; если такой карты нет - основную (Dion, 16010).

Так запрос тренировки (карта 16023) уйдёт в комнату 16023, если она
зарегистрирована, и в Dion - если нет. Сейчас в `config/services/room.json`
одна комната (`"mode": "dion"`), поэтому любой запрос попадает в Dion.
Чтобы добавить вторую, нужен второй менеджер комнат со своим
`config/services/room.json` (свои `room_id`, `mode` и `api_port`).

## Важные выводы

1. **Список режимов и карт живёт на клиенте.** В приветственных блобах
   сервера (`0x5fb`, `0x54e1`, `0x73aa`, `0x73b0`, `0x2ef`) нет ни id карт
   (16007/16010/16021/16023), ни названий ("Training", "Custom", "Vera").
   Поэтому "Training", "Vera" и "Custom" стали доступны у игрока только
   после перезапуска клиента - это его локальное состояние, а не ответ
   сервера.
2. **Серверу достаточно двух вещей:** принять `0x6e29` (он уже содержит
   режим, перспективу, тип и карту) и отдать адрес комнаты в `0xd77/0xd76`.
   Карта в запросе должна совпадать с картой комнаты, иначе клиент уходит.
3. **Отмена работает:** `0x6e2b` -> `0x6e2c`, и MATCH_SYNC после отмены не
   уходит.
4. **Строка в протоколе всегда** `u32 длина + ASCII + NUL` - так передаются
   имя, пароль сессии, поиск друга и бонусный код.
5. Запросы `0x7021`, `0x703b`, `0x702b`, `0x7149` серверу отвечать не нужно:
   клиент использует их для своей локальной части интерфейса.
