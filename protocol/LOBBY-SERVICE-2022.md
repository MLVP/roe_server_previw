# Объединённый сервис лобби и пользователи (ROE_local_test_2)

Дата: 2026-10-22. Сервер остаётся целиком на Python; C# и .NET из проекта
убраны.

## Что изменилось

Раньше в стеке было три отдельных процесса:

| процесс | порт | роль |
|---|---|---|
| `LobbyEmulator.dll` (C#, .NET 8) | 9001 | базовые ответы лобби: IT/SA/DT |
| `heartbeat_probe_2022.py` (прокси) | 8001 | MITM-логика лобби: команда, подбор, JOIN_INSTANCE, часы, личность |
| `game_endpoint_probe_2022.py` | 18001/UDP | игровая комната |

Теперь лобби и прокси — **один процесс**. `tools/heartbeat_probe_2022.py`
принимает подключение клиента на `127.0.0.1:8001` и сам отвечает на базовые
пакеты лобби через `server/directory/lobby_login_2022.py` (Python-портал
`LobbyPreData.cs` из MIT-исходников в `search/`).

Удалено из проекта:

- `server/lobby/LobbyEmulator.Sdk/` (csproj, DLL, obj/bin);
- `.tools/dotnet/` (70 МБ) и установка .NET в `tools/bootstrap.ps1`;
- сборка DLL в `tools/windows_launch.py`;
- шаг «lobby» из списка контролируемых процессов лаунчера.

Справочник с исходниками на C# переименован в `search_/` и в серверный код
не входит: в самом сервере C# нет, остались только лицензия MIT и
пояснение (`search_/README.md`).

Порт 9001 больше не используется: `check-login-room.cmd`, `stop-server.cmd`
и проверка готовности комнаты переведены на признак готовности прокси.

## Личность по uid

Клиент объявляет `-uid=<uid>` в логине. Это значение лежит в DT-кадре
`Login_Hello_v3` (код `0x2f0`) и читается как BE32 по смещению **42**
расшифрованного payload. Проверено на живом клиенте: `-uid=4242` → `0x1092`
по этому смещению.

Порядок обработки соединения:

1. клиент шлёт `IT` → сервис отвечает `SN`;
2. клиент шлёт `SA` → сервис отвечает `ID` + `CK` (`private/lobby-ck.bin`);
3. клиент шлёт `DT` (логин) → сервис разбирает uid, отвечает четырьмя
   приветственными DT-кадрами (один раз на соединение, как `Init` в C#);
4. сервис ищет uid в `users/registry.json` и подставляет личность
   в приветствие: `actor_uid` в `ENTER_GAME_RSP` (`0x32b`, смещение 22) и
   ник в lobby-профиле (`0x2ef`);
5. дальше идёт игровая часть лобби (команда, подбор, JOIN_INSTANCE, часы).

Если uid в реестре не найден, остаётся личность профиля комнаты
(`--actor-uid`), а в журнале появляется событие `login_unknown`.

Журнал событий сессии: `rooms/<room>/sessions/<id>/lobby/*/events.jsonl`,
событие `login_identity` содержит `uid`, `actor_uid` и `nickname`.

## Менеджер пользователей

`user.cmd` (обёртка над `tools/roe_user_manager.py`) создаёт папку
пользователя и оба идентификатора:

```bat
user.cmd add alice --nickname Alice
user.cmd add carol --nickname Carol --uid 4242
user.cmd list
user.cmd show alice
user.cmd remove alice
```

Что создаётся:

- `accounts/<name>/account.json` — аккаунт в общем формате `accounts_2022`
  (тот же `actor_uid`, поэтому лаунчер и косметика работают с тем же
  профилем);
- `accounts/<name>/cosmetics.json` — внешний вид;
- `users/<name>/user.json` — профиль с обоими id;
- `users/registry.json` — реестр `uid -> профиль`, его читает сервис.

Значения по умолчанию: `uid` — случайный из диапазона 1000..2^31-1,
`actor_uid` с базы `0x515BB100000000` (уникальный). Оба id можно задать
вручную (`--uid`, `--actor-uid`).

## Ярлык клиента

`lnroeuser.cmd` (обёртка над `tools/lnroeuser.py`) создаёт ярлык Windows:

```bat
lnroeuser.cmd -uid 4242 -f "C:\Program Files (x86)\Steam\steamapps\common\Ring of Elysium" -o "%USERPROFILE%\Desktop\ROE carol.lnk"
```

Ярлык запускает `Europa_Client.exe` с `-language=en -garena -uid=<uid>
-server=<host:port>` и рабочей папкой = папка игры. Адрес лобби задаётся
`-s` (по умолчанию `127.0.0.1:8001`). Файлы игры не меняются.

## Запуск с несколькими игроками

```bat
user.cmd add alice
user.cmd add bob
serve-login.cmd --room-mode dion --room-profile awp
play-account.cmd alice
play-account.cmd bob
```

`play-account.cmd <имя>` берёт uid из `users/registry.json` и передаёт
клиенту `-uid=<uid>`. Оба клиента держат одно TCP-соединение каждый и
получают разные личности; комната (UDP 18001) общая.

Замечание по клиенту: окно запускается **видимым**. У клиента есть
заставка на 30-40 секунд, и её нужно пропустить вручную; скрытое окно
(`-WindowStyle Hidden`) заставку не показывает.

## Телеметрия Tencent (TQMCenter)

Клиент поднимает `TQM64\TQMCenter_64.exe` - сборщик крашей и телеметрии
Tencent (GbSpy64.dll -> `bugly-tqm-client`, конфиг `GameBabyConfig64.dat`,
выгрузка на `gamer.qq.com/TQM` и `pc.bugly.qcloud.com`). Он резервирует
около 1 ГБ приватной памяти под дампы; в диспетчере задач это видно как
«память», в реальности занято около 30 МБ (приватный working set ~4 МБ).

Готовых настроек нет: `TQMDisable.ini` в папке игры на запуск не влияет, а
в схеме конфига (`GameBabyConfig64.dat`) есть только `GameName`, `AppId`,
`DomainUrl`, `IgnoreDlls`, `LogOutput`, `Version` - выключателя нет.

Работающий способ - запрет запуска самого файла:

```bat
telemetry.cmd off     - запретить запуск (по умолчанию делает лаунчер)
telemetry.cmd on      - вернуть как было
telemetry.cmd status  - показать состояние
```

Запрет ставится правами на `TQM64\TQMCenter_64.exe`
(`icacls ... /deny <user>:(X)`): ни лишнего процесса, ни правки файлов игры.
Проверено: клиент без него стартует и входит в комнату как обычно
(вход в лобби ~56 с), процесса `TQMCenter_64.exe` не появляется.

`windows_launch.py` делает это сам перед запуском клиента
(`--keep-telemetry` отключает поведение).

## Как клиент попадает в игру без хуков

Никаких хуков и патчей лаунчера нет: клиент запускается обычной строкой
`Europa_Client.exe -language=en -garena -uid=<uid> -server=127.0.0.1:8001`.
Всю игровую часть отвечает сервер:

| кадр | назначение |
|---|---|
| `0x32b` ENTER_GAME_RSP | личность игрока (actor_uid, ник) |
| `0x701e` / `0x7030` | ответы на CREATE / PULL_INFO команды |
| `0x6e2a` / `0x6e2c` | начало и отмена подбора |
| `0x6e2d` MATCH_SYNC | «матч найден» |
| `0xd77` / `0xd76` | уведомление о комнате и ответ с её адресом |

Автостарт матча - тоже серверный: `--auto-match-seconds N` заставляет
сервис через N секунд сам послать MATCH_SYNC, поэтому игроку не нужно
нажимать Play.

## Логи пакетов

- `rooms\<room>\sessions\<session>\packets.log` - одна строка на пакет:
  метка времени, направление (`client_to_server` / `server_to_client`),
  источник и hex пакета.
- `rooms\<room>\sessions\<session>\lobby\<run>\events.jsonl` - события
  (ответы, личность, косметика, пропуски).
- API: `GET /api/packets?tail=100` и `GET /api/logs?name=proxy&tail=100`.

## Заставка и видео-вступление

Интро - это UI-сценарий прелогина: логотип `//Video//Aurora_logo.usm` и
ролик `//Video//Trailer.usm` (файлы лежат в SFC, не в папке игры). Отдельной
настройки или ключа командной строки для его отключения нет: код клиента
запакован VMProtect, а известные ключи ограничены `-language`, `-garena`,
`-uid`, `-server`, `-windowed`. Пропуск - только вводом (клик или клавиша)
в видимом окне.


## Просмотр логов пакетов

`tools/packet_log_view_2022.py` разбирает `packets.log`: собирает кадры из
TCP-чанков, расшифровывает их сессионным ключом и печатает время,
направление, код сообщения с названием и поля (uid, login_id, actor_uid).

```bat
.tools\python\python.exe tools\packet_log_view_2022.py rooms\dion-1\sessions\<id>\packets.log --summary
.tools\python\python.exe tools\packet_log_view_2022.py rooms\dion-1\sessions\<id>\packets.log --tail 40
.tools\python\python.exe tools\packet_log_view_2022.py <log> --direction client_to_server --code 0x2f0
.tools\python\python.exe tools\packet_log_view_2022.py <log> --json
```

Коды сообщений: `0x2f0` логин (login_id по смещению 42), `0x32b`
ENTER_GAME_RSP (actor_uid по смещению 22), `0x2ef` профиль с ником,
`0x1f5f` часы, `0x1f75` heartbeat, `0x702f`/`0x701d` команда, `0x6e29`
запрос подбора, `0x6e2d` MATCH_SYNC, `0xd75`/`0xd76` вход в комнату.

У части клиентских сообщений (часы, `0x702f`) поле по смещению 22 содержит
метку времени, а не uid; настоящий uid берётся из `ENTER_GAME_RSP`.


## Запуск матча клиентом

Клиент шлёт запрос подбора `0x6e29` (20 байт: тип, ?, перспектива, ?, ?),
где перспектива 1 - TPP, 2 - FPP. Сервис отвечает `0x6e2a` (оценка ожидания
по умолчанию 5 с - локальный сервер отвечает сразу), затем `0x6e2d`
(MATCH_SYNC) и `0xd77` с адресом комнаты; клиент отвечает `0xd75`, сервер -
`0xd76` с маршрутом в игровую комнату. Отмена - `0x6e2b`, ответ `0x6e2c`
(отмена принимается и после того, как матч найден).

Запрос `0x702f` (PULL_INFO) до `CREATE` намеренно не отвечается: клиент
считает, что состоит в команде, и ломает меню режимов.

Проверка тракта без клиента:

```bat
.tools\python\python.exe tools\lobby_flow_check_2022.py --uid 611567691 --actor-uid 0x515bb16f306f05
```




## Горизонтальная структура: три службы

Сервер разложен на три независимые службы, у каждой свой конфиг:

| служба | порты | конфиг | что делает |
|---|---|---|---|
| сервер аккаунтов | 8099 HTTP | `config/services/accounts.json` | пользователи, регистрация, профили |
| лобби | 8001 TCP + 8010 HTTP | `config/services/lobby.json` | логин, личность, меню, подбор, адрес комнаты |
| менеджер комнат | 18080 HTTP | `config/services/room.json` | игровые комнаты, сцены, погода, техника, команды |

Запуск всех трёх - один скрипт:

```bat
serve-all.cmd
```

Он поднимает три процесса, ждёт готовности каждого и печатает адреса.
Остановить - `stop-server.cmd` (или Ctrl+C в окне `serve-all.cmd`).

Связь между ними: менеджер комнат после готовности регистрирует комнату
в лобби - `GET http://127.0.0.1:8010/api/room?route=0:127.0.0.1:18001&
map_id=16010&instance_id=1`, - и лобби отдаёт этот адрес клиенту в
JOIN_INSTANCE. Поэтому лобби живёт своей жизнью и не перезапускается
вместе с комнатой.

API лобби (8010):
- `GET /api/status` - состояние: игроки, счётчики, зарегистрированная комната;
- `GET /api/players` - список игроков с uid/actor_uid/ником;
- `GET /api/room?route=...&map_id=...&instance_id=...` - регистрация комнаты
  (её вызывает менеджер комнат).

Журналы: лобби - `lobby\<запуск>\`, комната - `rooms\<room>\sessions\<session>\`.

## Разделение лобби и комнат

Лобби и комната - разные вещи, и журналы у них разные.

```
roe_accounts.py serve            8099   сервер логина и аккаунтов
  room_manager.py                18080  комнаты: endpoint, сцены, игроки
    windows_launch.py --services-only
      lobby (объединённый сервис) 8001  лобби: TCP, логин, личность, подбор
      endpoint                     18001 игровая комната: UDP, сцена, актор
```

- **Лобби** - постоянная служба: логин, личность, меню режимов, подбор,
  выдача адреса комнаты. TCP-трафик клиента пишется в `lobby/<запуск>/`.
- **Комната** - короткоживущая сессия матча: UDP-трафик, сцена, игроки.
  Её файлы в `rooms\<room>\sessions\<session>\`.

Папка лобби:

| файл | что это |
|---|---|
| `lobby\<запуск>\packets.log` | TCP-пакеты лобби (логин, подбор, JOIN) |
| `lobby\<запуск>\events.jsonl` | события: личность, ответы, косметика, подбор |
| `lobby\<запуск>\status.json` | счётчики сервиса |
| `lobby\<запуск>\service.log` | stdout/stderr сервиса |
| `lobby\current.json` | указатель на текущий запуск лобби |

Папка комнаты:

| файл | что это |
|---|---|
| `rooms\<room>\sessions\<session>\packets.log` | UDP-пакеты комнаты |
| `rooms\<room>\sessions\<session>\endpoint.log` | игровая комната |
| `rooms\<room>\sessions\<session>\scene\` | события сцены и актора |
| `rooms\<room>\sessions\<session>\launcher.log` | запуск стенда |

Комната перезапускается (новый session id) при простое 30 с; активность
считается по обоим журналам - UDP комнаты и TCP лобби, иначе игрок в меню
лобби считался бы простаивающим.

Пути к лобби видны в `GET /api/status` (поле `lobby`) и
`GET /api/logs?name=proxy&tail=100`.

## Где лежат логи лобби

Всё в папке сессии комнаты `rooms\<room_id>\sessions\<session_id>\`:

| файл | что это |
|---|---|
| `packets.log` | журнал пакетов лобби: одна строка на TCP-чанк (время, направление, hex) |
| `lobby\<запуск>\events.jsonl` | события сервиса: личность, ответы, косметика, подбор, JOIN |
| `lobby\<запуск>\status.json` | счётчики: соединения, heartbeat, team/match/join, личности |
| `lobby\<запуск>\packets.log` | копия пакетов от самого сервиса лобби |
| `proxy.log` | stdout/stderr объединённого сервиса лобби (старт, ошибки) |
| `endpoint.log` | игровая комната (UDP 18001) |
| `launcher.log` | запуск стенда |

`<запуск>` - подпапка вида `20261022T030038-heartbeat-ff3a2535` (время запуска
сервиса и случайный суффикс). Новая сессия создаётся при каждом старте
комнаты, поэтому старые логи не перетираются.

То же самое через API комнаты:
`GET /api/packets?tail=100` (пакеты), `GET /api/logs?name=proxy&tail=100`
(журналы), `GET /api/status` (состояние комнаты).

Разбор пакета в читаемый вид:
`tools\packet_log_view_2022.py <путь к packets.log>`.

## Ограничения

- Смена TCP-ключа (`CHGSKEY`/TEA) не реализована.
- Живая вставка лута и техники в идущий матч не реализована: `/api/spawn/request`
  только записывает запрос.
- Карта Kill Zone (16007) использует общие с Dion данные сцены.
- Идентичность выдаётся по uid из логина; подмена клиента на лету
  (MITM) не требуется и не выполняется.
